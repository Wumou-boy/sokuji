# Sokuji 会议翻译选型记录

**决定** · 保留 `qwen3.8-livetranslate-flash-realtime` 作为 Sokuji 的会议翻译模型。对照方案是百炼团队版 Token Plan 的 `qwen-audio-3.0-realtime-plus`。两款模型在样本上的字幕事实保留率相同，3.8 的优势是更早提供字幕，以及更完整地输出连续译音。

## 2026 年 11 月 23 日实测

在同一台 Windows 电脑和同一网络上，通过北京地域的两个 WebSocket 网关成对发送同一份 16 kHz、16-bit、单声道 PCM，每 100 ms 一块。两边自动模式均确认接受 `server_vad`、阈值 0.5 和静音时长 600 ms。两个服务使用各自的译文配置、音色和网关，数据代表这两个接入方案的实际表现。

字幕和连续译音使用同一段 36.941 秒测试音频，按英语、日语、中文、英语的顺序输入，目标是简体中文。按键译音使用同一段 7.882 秒中文音频，目标为英语。每个场景做 3 轮配对，共 9 对、18 个会话。按键测试在相同的音频边界提交，Audio 3.0 按协议在提交后发送 `response.create`。[LiveTranslate 事件参考](https://help.aliyun.com/zh/model-studio/live-translator-client-events) · [Audio 3.0 接入文档](https://help.aliyun.com/zh/model-studio/qwen-audio-realtime-user-guides)

| 指标 | 3.8 LiveTranslate | 团队版 Audio 3.0 |
|---|---:|---:|
| 第一段开口到首条中文字幕增量，中位数 | **2.15 秒** | 4.25 秒 |
| 第一段开口到原文和译文都出现，中位数 | **2.15 秒** | 4.59 秒 |
| 最后一段结束到全部字幕生成完成，中位数 | **0.55 秒** | 0.75 秒 |
| 最终字幕原文与译文配对 | 21/21 段 | 21/21 段 |
| 按键译音首包相对松键时间，中位数 | **松键前 6.59 秒** | 松键后 1.20 秒 |
| 松键到收齐英语译音，中位数 | **0.13 秒** | 2.38 秒 |
| 连续译音完成且收到 PCM | **21/21 段** | 12/21 段 |
| 连续译音取消且未收到 PCM | **0/21 段** | 8/21 段 |

按音频里的四段语音逐段对齐，3.8 在 12 个对照片段中有 11 个更早返回译文，领先时间的配对中位数是 **0.48 秒**。首段英语的提前量为 **2.05–2.10 秒**，第三轮的日语是例外，3.8 晚 **0.66 秒**。两边各通过 **39/39 项**字幕事实核对，包括会议时间、帧率、HDR 否定信息和集合要求。

团队版在三轮连续出声测试里各有 3 段响应被取消。9 个取消中，8 个完全没有 PCM，1 个只返回了部分音频，这 9 段对应的字幕仍然有终稿。3.8 在松键前已开始返回译音，实际从何时播放取决于 Sokuji 的音频路由和缓冲。

## 数据口径

[逐轮数据](results.json) 保留毫秒值、按 WAV 语音位置对齐的字幕结果、语音响应的结束状态和 PCM 字节数。首条中文字幕按首个非空译文事件计时，双语可用取原文与译文的首个非空事件中较晚的一个。连续译音完成要求 `response.done` 状态为 `completed`，且该响应有 PCM。

这轮测到本机接收模型数据。样本在安静条件下重复播放，Teams 对端的播放延迟、多人重叠、长会话和弱网表现尚未实测。
