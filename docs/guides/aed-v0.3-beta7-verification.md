# AED Translator V0.3.0-beta.7 · Windows Teams 收音

解压整个 ZIP，运行 `AED Translator.exe`。上游基线为 Sokuji 0.51.2，个人配置与历史仍使用当前 Windows 用户的 `%APPDATA%\Sokuji`。在「在线会议」选「两者」，对方音源选「自动」。需要观察外放回声时，选实体麦克风，并在回声抑制中选「全部」。

## Auto 在什么条件下切换

| Windows 上观察到的情况 | AED 的处理 |
| --- | --- |
| 一个 Teams 进程树可以抓到音频 | 从该进程树采集对方声音。 |
| 两个独立 Teams 进程树都在同一扬声器上发声 | 直接检查该播放设备是否只有 Teams 在发声。符合条件时按设备采集，并持续复查。同一棵树已在收音时，也会检查会议中新出现的第二棵树。 |
| Teams 有电平，单进程采集无声 | 检查 Teams 实际使用的物理播放设备。其他应用也在该设备上发声、归属不明或横跨不同设备时，暂停发送这个混合音源。 |
| 已启动会话，Teams 尚未发声 | Auto 继续搜索。符合条件的麦克风可提前使用 Windows 默认物理播放设备来消回声。选源成功后按实际输出重新绑定参考音。 |

OBS 的 Windows 应用音频抓取先匹配窗口，再从窗口取得 PID，按整棵进程树回环采集。播放设备采集是另一条路径。AED 沿用了同一组 Windows 接口，自动选源、多根 Teams 的判定及麦克风 AEC3 属于 AED 的实现。此次也调整了原生 helper 的取包循环，在事件超时后检查是否有待读包或设备失效。[OBS 应用音频抓取指南](https://obsproject.com/kb/application-audio-capture-guide) · [OBS Windows WASAPI 实现](https://github.com/obsproject/obs-studio/blob/master/plugins/win-wasapi/win-wasapi.cpp)

## 公司测试通话和日志回放

11 月 28 日的现场报告有 75 个采样点，30 个达到 Teams 电平阈值 0.012。这 30 个点都能看到同一扬声器上两条 Teams 会话同时有声。旧报告没有保存进程树关系，现场的 75 次轮询均未连上 AED。会后能查到一对跨角色的高度相似原文，时间相差约 1.97 秒。旧报告无法还原当时使用的 AEC 后端。

将 75 组实际电平分别送入新版选源代码。进程标识与进程树关系为构造值，进程音频探针模拟为静音。把两条有声会话归到同一棵树或两棵树，两个场景都在 30 个有声点选对了端点。在同一设备加入另一个有声应用后，30 个有声点均拒绝混音。此回放验证选源决策，无法还原现场的音频波形或测量公司的消回声效果。

## 本机 Windows 实测

将两个测试音（523 Hz 和 997 Hz）从同一测试进程树播放，另一个独立进程同时播放 1481 Hz，全部定向到已确认空闲的 Realtek 物理输出。源文件为合成正弦音。新版原生 helper 输出的单声道 PCM 只在内存中做频谱分析。

| 实际采集方式 | 523 Hz 幅度 | 997 Hz 幅度 | 独立进程 1481 Hz 幅度 |
| --- | ---: | ---: | ---: |
| 指定进程树 | 0.07889 | 0.07857 | 0.000021 |
| 指定物理播放设备 | 0.07996 | 0.07983 | 0.07959 |

两种采集在同一台机器上有明显差别。两路目标声音进入进程采集，独立进程的测试音低约 72 dB；设备采集则收到三种声音。这也是 Auto 回退到扬声器前需要复查其他应用的原因。

在打包 EXE 中首次测试双根时复现了 Auto 超时。两个合成播放进程都在发声，强制选 Realtek 可以收到峰值 0.160，而打开回环后 Windows 还把 AED 的采集助手列为活跃的播放会话。该行的电平约 0.160，跟随它正在读取的两个音源之和，触发了旧的竞争音源判断。

修复后，AED 核对仍存活的子进程 PID、可执行文件，并确认该会话只归属这个进程，随后将自己的采集助手从竞争音源中排除。其他同名进程、归属不清的共享会话继续参与判断。新版会议报告将同一包里的采集助手单独计数。

用随包 EXE 和现有用户配置，再通过应用的 Auto 入口复验。测试播放器使用 Teams 的进程名来走同一条识别分支，内容为 Realtek 上的合成音。单根得到应用音频，峰值 0.080；双根得到受保护的扬声器音频，峰值 0.160。双根不变、再加入独立发声程序时，Auto 在整个检查窗口内都没有打开混音。测试使用本地音频诊断，全程没有调用翻译服务。

同一 EXE 在实体麦克风和 Realtek 输出上又运行了 5.5 秒回声诊断。Windows 提供了 550 个参考音频块，浏览器自带回声处理已关闭，65 个麦克风音频块全部经过 AEC3。这次麦克风原始 RMS 只有 0.00075，因此用该结果确认 AEC3 确实接管，公司的笔记本外放串音改善幅度仍待现场测量。

独立运行随包相同的 AEC3 WASM 和合成双讲回归。固定 20 ms 延迟及双抽头房间响应下，仅有远端声音时输出降低 24.9 dB；双讲时输出相对近端参考的电平为 −1.7 dB。该数值描述这组合成信号，公司的笔记本扬声器和麦克风仍需现场验证。

## 取得会议报告

从同一解压目录运行 `AED-Teams-Live.cmd`。AED 已经打开时，脚本会尝试连接这个实例；尚未打开时，脚本用原配置启动它。命令窗口显示“已连上 AED”后即可照常使用。会后在桌面取得 `AED-Teams-Live-*.txt`。若使用 Teams 测试通话，可在播报时保持安静，然后在录音提示后说一句，用来同时观察对方串音和自己发言是否保留。

报告含 Windows 扬声器电平、Teams 的有声进程树数量、其他应用竞争计数、Auto 实际路径和跨角色字幕匹配计数。会中接入也会读取当前麦克风实际约束、参考音源和 AEC3 成功处理的 10 ms 帧计数。连续两次读数增长可以确认这段时间内处理过麦克风音频。报告不写入录音或字幕原文。没有观察到运行中的 AED 会话时，会话交叉统计显示为空，Windows 电平单独计数。离线设备排查仍可运行 `AED-Audio-Report.cmd`。

打包版按普通方式启动后，实跑同目录 CMD，成功连接原进程。9 次采集均读取到 Windows 扬声器电平，后 8 次也连上了应用。诊断连接仅开放监测所需的命令。应用原有音频模式和空闲时的日志偏好均得到保留。

13 个音频及控制相关测试文件共 272 项通过，另有两项 Windows CMD 集成测试通过。整仓 TypeScript 检查仍有 93 条既有诊断，对照 beta.6 的错误文件、代码和内容一致。
